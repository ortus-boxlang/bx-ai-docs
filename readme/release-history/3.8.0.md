# 3.8.0 Release Notes

**Released:** not yet released

BoxLang AI 3.8.0 teaches the MCP client to **sign in with OAuth**. Servers that ask each person to sign in (mail, calendars, issue trackers) can now be used, and one shared client can sign in every person on their own, so an agent that serves many people uses each person's own account.

It also fixes a memory mix-up: gateway chats, and `window`, `summary` and `jdbc` memory, used to share one bucket across users and conversations. Each call is now keyed by user and conversation. `providers.<name>` settings now reach every provider, `AiModel.getConfig()` has a `providerId` you can pass back to `aiService()`, and the MCP server over STDIO now speaks clean JSON-RPC.

---

## ⚠️ Migration

* **A gateway turn is now keyed by user and conversation.** `GatewaySession` ran every turn with only `{ threadId }`, so the agent's memory (keyed by user and conversation) was one shared bucket: every chat on every platform saw every other chat's messages. Each turn now runs with a `conversationId` and, when the platform names the sender, a `userId`. The conversation is the chat namespaced by its gateway (`telegram:42`), plus the platform thread when there is one (`telegram:42:topic-7`), so a Telegram forum topic or a Slack thread is its own conversation. `threadId` still names the run (queueing, cancel, steer, checkpoints).
* **Conversations a gateway kept in the old shared bucket are not found under the new keys.** Override the public `resolveConversationId( message, sourceGateway )` to move a chat to another conversation, or `turnOptions( message, sourceGateway, threadId )` to name the identity another way, for example with a platform-qualified user id. See [Gateway Sessions](../../main-components/gateway-sessions.md).
* **Jdbc memory keeps each user and conversation in a row of its own.** The `userId` and `conversationId` of `add()`, `getAll()`, `clear()`, `trim()`, `summarize()` and the other calls were ignored by `jdbc` memory, so every user of an agent shared one bucket. A call that names another scope now reads and writes the row `<key>::<userId>::<conversationId>`, with `user_id` and `conversation_id` filled. No table change is needed. Messages an agent kept in the old single row stay under the memory's own key and are no longer returned for a call that names a user or a conversation. `JdbcMemory.summarize()` for another scope no longer throws `JdbcMemory.UnsupportedScope`. See [Memory Systems](../../main-components/memory/README.md).
* **Window and summary memory keep each user and conversation apart.** `window` is the default memory, so an agent run with `{ userId, conversationId }` (as a gateway does) used to show Bob all of Alice's messages. A call that names another user or conversation now gets a list of its own, and `hybrid` memory follows. A call with no ids, or with the ids the memory was built with, uses the memory's own list as before. These lists live in the process: they are lost on a restart and are not shared between servers (use `cache` or `jdbc` memory for that). Messages gathered under per-call ids before this are in the memory's own list.
* **`providers.<name>` settings win less and apply more.** Options you pass to `aiService()` or in a profile now win over `providers.<name>.options` (they only fill the gaps), and `defaultParams` and `providers.<name>.params` now win over a provider's built-in chat defaults. See [Configuration](../../getting-started/configuration.md).
* **If you wrote your own `IMCPClient`**, add the optional argument `struct context = {}` to `send( tool, args, context )`. `MCPTool` now passes it. Without `withOAuth()` nothing else changes.

## ✨ New Features

### 🔑 OAuth for MCP Clients

`withOAuth()` follows the [MCP authorization specification](https://modelcontextprotocol.io/specification/latest/basic/authorization). The client finds the authorization server from the MCP server's metadata, gets a client id (one you give, a Client ID Metadata Document, or Dynamic Client Registration), signs the person in with PKCE and the `resource` parameter, checks the issuer in the callback, and sends `Authorization: Bearer` on every request. A token that is about to expire is refreshed first, and a `401` refreshes it and tries once more.

```javascript
mcpClient = MCP( "https://mail.example.com/mcp" ).withOAuth( {
    redirectUri : "https://app.example.com/oauth/callback"
} )

// send the person to sign in
started = mcpClient.startAuthorization( "alice" )
location( started.authorizationUrl )

// at your callback route
mcpClient.completeAuthorization( url.code, url.state, url.iss ?: "" )

// from now on the calls carry Alice's token
mcpClient.send( "inbox", {} )
```

Your code does the browser step (sending the person and receiving them back). The client does the rest.

### 👤 One Client, Every Person

The `subject` option says whose tokens a call uses. `send( tool, args, context )` has a new optional `context`, and the tools an agent builds from an MCP server pass `{ chatRequest }`:

```javascript
mcpClient = MCP( "https://mail.example.com/mcp" ).withOAuth( {
    redirectUri : "https://app.example.com/oauth/callback",
    subject     : ( context ) => context.chatRequest.getUserId()
} )
```

Each person signs in once, and from then on the agent reads **their** mail, not anyone else's. With `withHandshake( true )` each person also gets an MCP session of their own.

### 🗄️ Token Stores

Tokens, the client registration and the sign ins waiting for their callback live in an `IMCPTokenStore`: three methods (`get`, `set`, `remove`), so a store that encrypts is easy to write.

| Store | Where | Choose it with |
|---|---|---|
| Cache (default) | A BoxLang cache: memory, or Redis and others | `store: "cache"`, `storeOptions: { cacheName }` |
| File | One JSON file per record, owner-only permissions where the system has them | `store: "file"`, `storeOptions: { path }` |
| JDBC | A table, created when missing | `store: "jdbc"`, `storeOptions: { datasource, table }` |
| Your own | A class that implements `IMCPTokenStore` | `store: "my.Store"` or an instance |

The file and JDBC stores keep tokens as plain text. Protect them, or write a store that encrypts.

### 🤖 Agents

`oauth` works in an agent's MCP server config:

```javascript
agent = aiAgent(
    name       : "mail-agent",
    model      : aiModel( provider: "openai" ),
    mcpServers : [
        { url: "https://mail.example.com/mcp", oauth: { redirectUri: "https://app.example.com/oauth/callback", subject: ( context ) => context.chatRequest.getUserId() } }
    ]
)
```

A server nobody has signed in to yet cannot list its tools, so the agent starts without them. After signing in, hand the signed in client to the agent with `agent.withMCPServer( mcpClient )`.

### 🔎 `providerId` in `getConfig()`

`AiModel.getConfig().provider` is the service display name (`OpenAICompatible`, `DockerModelRunner`), and `aiService()` and `aiChat()` do not accept it for those two providers. `getConfig().providerId` is the id every provider is registered under, so it can go straight back into the API. `provider` is unchanged.

```javascript
config = aiModel( "docker" ).getConfig()
config.provider     // "DockerModelRunner"
config.providerId   // "docker"
aiService( config.providerId )
```

### 🧠 Memory per User and Conversation

`jdbc`, `window` and `summary` memory now honor the `userId` and `conversationId` of each call, as `cache`, `file` and `session` memory already did. Two more additions:

* `maxConversations` for `window` and `summary` memory: how many other users' and conversations' lists one memory keeps in the process, `1000` by default (`0` for no limit). Past it, the least recently used list is dropped. The memory's own list never is.
* A sub-agent now runs for the same user and conversation as its parent, so a sub-agent with its own memory no longer shares one bucket among everyone who delegates to it. `AiBaseRequest` has a new `conversationId` property and `getConversationId()`.

```javascript
memory = aiMemory( memory: "window", config: { maxMessages: 20, maxConversations: 500 } )
```

### 🔑 `discoverySubject` for MCP OAuth

`withOAuth( { discoverySubject : "alice" } )` (a name, or a function with no arguments) says whose tokens a call with no context uses, such as listing the tools when an agent starts. Before, such a call always used the subject `"default"`.

### 📡 A New Event

`onMCPAuthorizationRequired` fires when a person has to sign in or grant more scope, with `reason` (`no_token`, `unauthorized` or `insufficient_scope`), `subject`, `scope` and the `client`. See the [event reference](../../advanced/events.md#72-onmcpauthorizationrequired).

📖 Read [OAuth Sign In](../../mcp/client/oauth.md) for the full flow, the options, the errors and how to write your own store.

## 🐛 Fixed

* **MCP server over STDIO wrote its logs to stdout.** Log lines between the JSON-RPC messages break a client. `MCPRequestProcessor::processStdio()` now moves the console log appenders to stderr before it logs anything. File logging is unchanged. See [Transports](../../mcp/server/transports.md).
* **MCP server answered notifications.** A message without an `id` (`notifications/initialized`, `notifications/cancelled`) got a `Method not found` error. A notification never gets a response now: `handleRequest()` returns an empty struct, STDIO writes nothing, and HTTP answers `202 Accepted` with no body.
* **`@mcpTool` tools lost their parameters.** A tool registered by `scan()` or `scanClass()` was listed with an empty `inputSchema`. It now lists the method's parameters with their type, whether they are required, and the `@paramName` hint as the description. See [Annotation-Based Discovery](../../mcp/server/annotation-discovery.md).
* **`providers.<name>` settings now apply to every provider.** A provider whose display name differs from its id never got its settings: `providers[ "openai-compatible" ]` and `providers.docker` were ignored, and `openai-compatible` fell back to `http://localhost:8080/v1`. Settings under both `providers.<slug>` and `providers.<service name>` are applied, and the slug wins. `defaultParams.model` is also sent now: the built-in `model` used to be merged in ahead of it.
* **Summaries stay with their conversation.** `summarize()` on `cache`, `file`, `session` and `jdbc` memory sent another conversation's summary to the model, emptied a short conversation, and lost the earlier summary on a new instance. The earlier summary is now read from the conversation's own stored summary message, and nothing is written when there is nothing to summarize. `window` and `summary` memory also keep their summary message when they trim.
* **Jdbc memory keeps every message when several threads add to one conversation.** Two adds to a new conversation could both insert its row and one failed with a primary key error, and concurrent adds could overwrite each other. Those writes now take a lock per datasource, table, key, user and conversation. Two processes writing to the same conversation at the same instant can still lose a message.
* **MCP OAuth in a web request.** The token request of a sign in was sent with an empty body under CommandBox and the MiniServer, because a form field argument was named `form`, a reserved scope there. Signing in works in a served app, not only in a script.
